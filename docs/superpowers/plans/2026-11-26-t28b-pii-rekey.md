# T28b — PII/HMAC Re-keying Pass and `RequestFingerprint` Key Ids Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move every customer's ciphertext and lookup hashes to the active PII key, safely and resumably; keep idempotent replays correct across an HMAC rotation; and print, per key id, whether that key can be retired.

**Architecture:**
- `idempotency_keys` gains `request_hash_kid` (V25). A claim records the active `kid`. A replay recomputes the fingerprint under the row's recorded `kid`, or under the legacy key when it is `NULL`.
- A maintenance runner in the `contract` module exists only when `serfira.maintenance.pii-rekey.enabled=true`. It runs once at startup under its own ShedLock lock with a `job_run` row:
  - a pre-flight census decrypts every customer and aborts with zero writes on a duplicate or an unreadable row;
  - `EXECUTE` re-keys page by page and verifies each row in its page's transaction;
  - every run ends with a retirement report.
- The census, the per-row verifier and the retirement verdict are pure classes with unit tests. Wiring and SQL are proven by two Testcontainers ITs that restart the application on one database with a different ring.

**Tech Stack:** Java 21, Spring Boot 4 (`ApplicationRunner`, `@ConditionalOnProperty`, `@ConfigurationProperties`, `JdbcClient`, `SpringApplicationBuilder`, `ApplicationContextRunner`), ShedLock 7.10.1, Flyway, PostgreSQL 16 with Testcontainers.

**Spec:** `docs/tasks.md` § "T28b — PII/HMAC re-keying pass and `RequestFingerprint` key compatibility (CR-11)". Its business rules come from:
- ADR-025 (key ring, D6 runbook, D7 two-phase envelope);
- ADR-004 (encryption only in the application);
- ADR-017 (single-use keys, expiry before comparison);
- ADR-007 (`request_hash` is a keyed digest);
- `04_GAPS_ADDENDUM.md` §9 (no PII in logs).

## Decisions (made here; the ADR-025 addendum records them)

1. **The migration is V25, not V24.** The spec says "V24", but V24 is T36's reporting indexes. `V25__idempotency_request_hash_kid.sql` adds `request_hash_kid VARCHAR(16) NULL` with `CHECK (request_hash_kid IS NULL OR request_hash_kid ~ '^[a-z0-9]{1,16}$')`. There is no backfill: `NULL` means legacy. The close-out corrects the task text.
2. **What "unexpired" means.** A fingerprint is unexpired when `expires_at IS NULL OR expires_at > now`. This mirrors `IdempotencyService`, which compares a row whenever `expiresAt == null || expiresAt.isAfter(now)`, so the report counts exactly the rows a replay could still compare.
3. **When a row is on target.** A customer row is on target when both envelopes start with `v2:<activeKid>:` and both lookup columns equal the active-key hash of the decrypted value. Everything else is re-keyed, including `v1:` rows while `k1` is active, so the legacy designation can be dropped later.
4. **`EXECUTE` refuses to run while `write-envelope=v1`** (ADR-025 D7: the pass writes `v2`). The refusal happens in the job, before any write, as a `PiiRekeyPreflightException`, and leaves a `FAILED/0/0` `job_run` row. `DRY_RUN` is allowed in either mode.
5. **The runner is a synchronous `ApplicationRunner`.** By the time runners run, the embedded server is already accepting requests, so the app serves during the pass, and tests see a finished run once `run()` returns. A failure is logged and recorded in `job_run`; it never stops the application. Trade-off: a readiness probe, if enabled, reports ready only after the pass. ADR-025 records this.
6. **Properties:**

   | Property | Default | Meaning |
   |---|---|---|
   | `serfira.maintenance.pii-rekey.enabled` | absent | `true` creates the runner; anything else creates no bean |
   | `serfira.maintenance.pii-rekey.mode` | `DRY_RUN` | `DRY_RUN` or `EXECUTE`; an unknown value fails startup |
   | `serfira.maintenance.pii-rekey.batch-size` | `500` | Page size, `≥ 1` |
   | `serfira.maintenance.pii-rekey.lock-at-most-for` | `PT10M` | ShedLock bound; the keep-alive provider extends it |

   The environment-variable forms are `SERFIRA_MAINTENANCE_PIIREKEY_ENABLED`, `_MODE` and `_BATCHSIZE`.
7. **Retirement verdict, per ring `kid`:**
   - the active key is `ACTIVE`;
   - any other key is `RETIRABLE` only when all of these are zero:
     - customer rows with an envelope under it (a `v1:` envelope counts under the legacy key);
     - customer rows with any hash off the active key (a global count, which is conservative and exact for a two-key ring);
     - unexpired fingerprints recorded under it (`NULL` counts under the legacy key);
     - unreadable rows (unknown `kid` or a failed decrypt);
   - otherwise it is `NOT_RETIRABLE`;
   - an unexpired fingerprint whose `kid` is not in the ring is `MISSING_FROM_RING`, because its replays will fail.
8. **`job_run` counters.**

   | Run | `status` | `records_processed` | `records_failed` |
   |---|---|---|---|
   | `DRY_RUN` | `COMPLETED` | 0 | 0 |
   | `EXECUTE` | `COMPLETED` | rows re-keyed | 0 |
   | Pre-flight abort | `FAILED` | 0 | blocking rows |
   | Any later abort | `FAILED` | rows committed so far | 1 |

9. **Customer-row writes bypass JPA.** They go through native `JdbcClient` SQL on the raw columns, because the entity holds only plaintext and dirty checking would never fire. The SQL only stores values that the application encrypted and hashed.

## Global Constraints

- ADR-004: AES-GCM and HMAC run in Java through `PiiSecuritySupport`. Keys and plaintext never appear in SQL.
- Addendum §9: no NIK, phone, envelope or full 64-hex hash in a log line or an exception message. Kids, counts and customer UUIDs are allowed.
- ADR-017: an expired claim is rejected before its `kid` is resolved or its hash compared.
- The runner is the only writer of existing `customer` rows. It changes only `nik`, `nik_hash`, `phone`, `phone_lookup`, `updated_at` and `updated_by` (the `SYSTEM` user, `AuditContext.SYSTEM_USER_ID`, via `auditContext.runAs`).
- Time comes from the injected `Clock`, never from `now()`.
- `shared` must not depend on `contract`. The runner lives in `contract` and reads fingerprint usage from `shared.idempotency`.
- Keyset SQL never uses `:param IS NULL` (X-13, `42P18`). Paging starts from `new UUID(0L, 0L)`.
- Any test that rebinds `PiiSecuritySupport` restores the test-profile ring in `@AfterEach` / `@AfterAll` with `PiiSecuritySupport.configure("0123456789abcdef0123456789abcdef".getBytes(UTF_8), "abcdef0123456789abcdef0123456789".getBytes(UTF_8))`. Never leave it `reset()`.
- Test key material for `k2` is the same as in `PiiKeyRotationIT`: `"rotation-k2-encryption-key-01234"` / `"rotation-k2-hmac-key-0123456789a"`.
- Commits carry no Co-Authored-By or "Generated with" lines.

## Review Focus

1. **A claim with `expires_at` `NULL`** (a row from before T24) is compared on every replay, so the report must count it as unexpired. If it were dropped, a key would be called retirable while a replay still needs it. Pinned by Task 1 `aClaimWithoutExpiryCountsAsUnexpired`.
2. **Paging past rows that are already on target.** After an aborted run, page 1 is on `k2` and later pages are not. The resume must advance its cursor by the rows it *scanned*, not the rows it *rewrote*. Otherwise it loops forever or skips rows. Pinned by Task 3 `aRerunResumesAndMovesEveryRemainingRow` (batch size 2, terminates, count 4).
3. **A `v1:` row while `k1` is still active** (phase 2 done, no rotation yet) still needs re-keying to `v2:k1:`. Otherwise the legacy designation can never be dropped. Pinned by Task 2 `aV1RowUnderAnActiveK1StillNeedsRekey`.
4. **A database error during the pass** (for example a unique violation, whose PostgreSQL message quotes `Key (nik_hash)=(<64 hex>)`) must not reach the log through the startup runner's error line. The runner logs the message only for its own abort exceptions. For anything else it logs the class name only. Pinned by Task 3 `aDatabaseErrorIsLoggedByClassNameOnly`.
5. **`SERFIRA_MAINTENANCE_PIIREKEY_ENABLED=true` / `_MODE=EXECUTE`** must enable the runner and bind the mode exactly like the properties form. This is how an operator turns it on. Pinned by Task 3 `theRunnerBindsFromEnvironmentVariables`.
